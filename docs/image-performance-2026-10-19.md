# 이미지 로딩 개선

## 확인한 병목

- 공개 기사 `/article/002`에서 폭 568px 및 276px인 갤러리 사진이 모두 `w_1200` 파일을 선택했습니다. 기존 `sizes`가 실제 칸 크기와 무관하게 데스크톱 1200px을 지정했습니다.
- 슬라이드 5장 모두 `src`가 있어, 화면 밖 사진까지 브라우저의 기본 lazy-loading 범위에 따라 내려받을 수 있었습니다.

## 변경

- 갤러리 열 수, 두 칸 차지 여부, 디자인 배치, 모바일 배치를 반영한 `sizes`를 사용합니다. 320px과 640px 후보도 추가했습니다.
- 브라우저가 불필요한 기본 파일을 먼저 선택하지 않도록 로딩 설정과 `sizes`를 이미지 주소보다 먼저 지정합니다.
- 첫 슬라이드 이외의 전송 주소는 보류합니다. 갤러리가 화면에 접근하면 현재 장과 다음 장을 준비합니다. 직접 이동 및 되돌아가기도 지원합니다.
- 보류 상태는 로딩 오류로 취급하지 않습니다. 원본 주소와 캡션은 보존합니다.
- 사용 중인 Cloudinary 이미지 호스트에 미리 연결합니다. 첫 화면 대표 이미지의 eager/high 우선순위는 유지합니다.

## 검증

- 브라우저에서 568px 및 276px 갤러리 칸이 `w_640` 파일을 선택하는 것을 확인했습니다.
- 기사 첫 진입 시 슬라이드의 다운로드 주소는 5개에서 1개로 줄었습니다. 갤러리 접근 시 2개가 준비되며, 이후 방문한 사진은 재사용합니다.
- 모바일 390×844에서 직접 5번째 슬라이드로 이동, 재시도 안내, 캡션 유지 및 보류 사진의 잘못된 오류 표시가 없는 것을 확인했습니다.
- 같은 기사 사진 3개를 같은 WebP 응답 조건으로 비교했습니다. 아래는 전체 사이트 평균이나 페이지 로딩 시간 개선율이 아닌 파일별 전송량 비교입니다.

| 표본 | 기존 1200px | 개선 640px | 감소 |
| --- | ---: | ---: | ---: |
| 1 | 228,406 bytes | 69,613 bytes | 70% |
| 2 | 169,848 bytes | 59,974 bytes | 65% |
| 3 | 241,324 bytes | 62,528 bytes | 74% |

전체 사용자 환경의 LCP나 실제 초 단위 개선은 별도 측정이 필요합니다. 고해상도 화면에서는 선명도를 위해 더 큰 후보가 선택될 수 있습니다. ImgBB가 원본을 반환하지 않는 사진은 이번 전송 최적화로 복구되지는 않습니다.
